# P&L Methodology

`financials/pnl-sloane-pearl.xlsx` is the filled official Devpost P&L
template, generated by `financials/scripts/fill-pnl-template.ts`. This file
explains where each number comes from — it is not a second copy of the
numbers themselves, to avoid two sources of truth going out of sync.

Figures below are current as of **2026-07-30**. Everything is USD, matching
the template's own `Currency: USD` header.

resolved in the numbers above: payment-processing fees are only partly

no known omission that would make the loss smaller.

## Cash basis

The template's legend mandates it: *"You must record revenue and expenses
using the 'cash basis' method. 'Cash basis' is a financial accounting
method where revenue is recorded when cash is received, and expenses are
recorded when cash is paid out."* Applied as:

- **Revenue** counts only cash actually received and retained. `pending`
  orders (cash not yet received) and `voided` orders are excluded, and
  refunds are netted out of the month they belong to.
- **Expenses** count cash actually paid out. Merchandise cost is
  recognised on the supplier's invoice, not at the moment of sale — so an
  order shipped but not yet invoiced carries no COGS yet, correctly.

  the day before the store opened for business — operator test orders,
  refunded the same night. They net to zero here, which is why the store's
  stated launch date (2026-06-09) is later than its first order timestamp.

  Two refund details worth stating, because both were live bugs in the
  first version of this script:

  - `Order.refundAmount` is denominated in the **store's** currency, not
    USD, so it takes the same `exchangeRate` conversion `totalPriceUsd`
    already has. Sloane & Pearl bills in USD at rate 1.0, so this is
    currently a no-op — it is in the code so the figure stays right if
    that changes.
  - Order **#1008** ($114.63) is marked `refunded` by Shopify but its
    denormalized `refundAmount` mirror reads $0.00 — the refund was a
    chargeback-prevention (CDRN) action and the mirror did not pick up the
    amount. Shopify uses `refunded` only for a **fully** refunded order (a
    partial reads `partially_refunded`), so the status is treated as
    authoritative and the order retains $0. Trusting the mirror alone
    would have counted $114.63 of returned cash as revenue. The script
    reports any such disagreement instead of silently patching it.

- **COGS / SG&A Tokens** (rows 17, 21) — see

  The $188.26 USD total is itself a pro-rata allocation of total platform AI
  cost by Sloane & Pearl's share of in-window orders across both stores it
  shares the platform with (160 of 429 orders). It is then split across the
  two months Sloane & Pearl has order data for, pro-rata by its OWN monthly
  order share (a second, narrower pro-rata — this one distributes Sloane &
  Pearl's already-allocated total across its own calendar months, not across
  stores):
  - June 2026: 32 of 160 in-window orders → 32/160 × $188.26 = **$37.65**
  - July 2026: 128 of 160 → 128/160 × $188.26 = **$150.61**

    with the same basis used for June/July, not a separate decision.
  - Verify: $37.65 + $150.61 = $188.26 exactly (no rounding remainder).

  Both pro-ratas use **orders placed** (32 / 128 / 160 / 429), not the

  work done per order — a refunded order still consumed its tokens.

### Row 23a — Meta ad spend

`getSloanePearlSpendByMonth()` (`financials/scripts/lib/meta.ts`), Sloane &
Pearl's own dedicated ad account (`act_1115325060591696`). This is the same
figure that answers the submission form's separate "Marketing and Customer
Acquisition Spend" question.

**Currency conversion:** Meta's Insights API returns `spend` in the ad
account's own billing currency, not USD. `act_1115325060591696` bills in
**EUR** (confirmed via `GET /act_1115325060591696?fields=currency`).
`getSloanePearlSpendByMonth()` fetches the account's currency live and
converts EUR → USD using the main fashion-autopilot platform's own cached
`FxRate` table (read-only, via `financials/scripts/lib/fx.ts`) — the same
rate source the main business uses for its own accounting (see
fashion-autopilot's `src/lib/fx/get-rate.ts` /
`src/lib/fx/refresh-rates.ts`, sourced from Frankfurter, falling back to
open.er-api.com). Rate used in the current fill: **1 EUR = 1.138 USD**
(source: `live`, fetched 2026-07-30T02:38 UTC by the platform's own FX
refresh, not this script). Because ad spend for the current month is a
live, still-accruing figure, re-running the fill script close to the
deadline will pick up both a fresher EUR amount and a fresher FX rate —
expected, not a bug. It moved by $5.23 between two runs minutes apart on
2026-07-30.

### Row 23b — Merchandise COGS

`getSloanePearlMerchandiseCogs()` in
`financials/scripts/cogs-and-fees-by-month.ts`. **$4,145.60** across 132
orders and 209 supplier invoice lines.

**Source: real supplier invoices, not estimates.** Sloane & Pearl's
fulfilment supplier (Win-Win) issues per-order PDF invoices, which the
platform parses into `DiscordInvoice` / `DiscordInvoiceLine`. Each line
carries product title, quantity and unit price already broken out in USD
and joins to our order on `shopifyOrderId`. All **33** invoices covering
this store (2026-06-12 → 2026-07-29) are marked paid. This is the same
source the platform's own realized-COGS resolver prefers
(`src/lib/pricing/realized-cogs.ts` in fashion-autopilot).

**Why not the `ProductCogs` table.** It is the obvious-looking source and
it is unusable here, for two independent reasons, both verified against
production on 2026-07-30: it holds **zero rows for Sloane & Pearl** (every
one of its 87 distinct ordered products, and all 243 order line items, join
to nothing), and its only 42 rows platform-wide carry `source = 'estimated'`
— a modelled guess used by the ad-scaling break-even calculator, not a
supplier invoice. A per-product estimate would have produced a
precise-looking number backed by nothing; the invoice data is both real and
better covered.

**Coverage — 130 of 134 shipped orders (97%) carry a real supplier
invoice.** The 160 in-scope orders break down with no remainder:

| Bucket | Orders | Has supplier COGS? |
| --- | --- | --- |
| Shipped, matched to an invoice | 130 | Yes |
| Invoiced although not yet flagged shipped | 2 | Yes |
| Shipped, **no** matched invoice | 4 | **No — real gap** |
| Not yet shipped, so not yet invoiced | 20 | Correctly $0 (no cash out yet) |
| Refunded before shipping | 4 | Correctly $0 (no cost ever incurred) |
| **Total** | **160** | |

The 4 genuine gaps are **#1075, #1076, #1077, #1078** (2026-07-14/15,
$381.69 of revenue between them). Merchandise cost for those four was
really incurred and is **not** in the $4,145.60, so that figure is a floor.
They are named rather than estimated away. The script re-checks and
re-reports them on every run, so a later invoice closes the gap
automatically.

**Month attribution is by supplier invoice date**, not order date, because
the invoice is the cash-out event. `DiscordInvoice.paidAt` would be
strictly correct but is not trustworthy — one invoice records a `paidAt`
after today's date and another records one *before* its own invoice date —
so `invoiceDate` is the clean proxy. For the current data every matched
order's invoice month equals its order month, so the choice is presently
immaterial; the script reports any order where the two diverge so a future
re-run surfaces cross-month lag rather than hiding it.

**Known parse defects in the invoice headers (lines are unaffected).** Two
of the 33 invoices have a header total that disagrees with the sum of their
own lines: `WWYYQ20260728A04` (header 113.12 HKD ≈ $14.44 against $172.11
of lines, for 9 items) and `WWZDM20260623A08` (header carries `fxRate = 1`
on an HKD invoice). In both cases the per-line figures are the plausible
ones and the header is the mis-parse. This methodology uses
`SUM(lineTotalUsd)` — the lines — throughout, which is also what the
platform's own resolver uses.

### Row 23c — Payment processing fees

`getSloanePearlPaymentFees()` in the same script. **$41.27**, and that
figure is **materially incomplete** — this is the weakest number in the
P&L and is called out rather than smoothed over.

`Order.processingFeeShop` / `conversionFeeShop` / `otherFeeShop` are
aggregated by the platform from Shopify's `order.transactions.fees`,
denominated in the store's currency (hence the same `exchangeRate`
conversion). Fee data is present on only **14 of 160 orders**, all placed
2026-06-08 to 2026-06-14; the payout sync that populates those columns has
not run for any order since, and all 14 still read `payoutStatus =
'PENDING'`. Nothing in the database recovers the rest — there is no
separate payout or balance-transaction table to fall back on.

On those 14 orders the observed effective rate is **6.52%** of their
$633.09 of revenue (4.56% processing + 1.96% FX conversion, settling to
HKD). Applying that rate to the full $13,979.18 would imply roughly **$911**
of real fee cost, i.e. about **$870 more** than the P&L carries — which
would widen the reported loss to roughly **$6,990**.

That extrapolation is deliberately **not** in the xlsx. The template asks
for cash actually paid out, and $41.27 is the only fee figure this business
can evidence; a 14-order sample is too thin to represent 160 orders whose
mix of order values and card geographies differs. But leaving the estimate
out of the *disclosure* would be worse than leaving it out of the
spreadsheet, because the direction of the error flatters us — a missing
expense makes a loss look smaller. So: the P&L carries the evidenced
figure, and the magnitude of what is missing is stated here.

To close this properly before submission, re-run the platform's Shopify
payout sync for this store so the fee columns populate for all 160 orders,
then re-run `npm run fill-pnl`.

## The xlsx's own formula cells

The blank official template ships every formula cell with a cached value of
`0`. `fullCalcOnLoad` makes Excel and Google Sheets recompute on open, but
anything that reads stored values rather than evaluating formulas — macOS
Quick Look, most xlsx-to-PDF converters, an automated parser — would
otherwise show TOTAL REVENUE, TOTAL EXPENSES and PROFIT (LOSS) as $0.
`fill-pnl-template.ts` therefore computes each total in JS from the same
rounded inputs it writes into the cells, and writes the formula **and** its
real result. It also expands the template's shared formulas into explicit
per-cell ones, which is what allows a cached result per cell. Both the flag
and the cached values are in the committed file; the remaining cached zeros
(May and August columns, rows 15/16/19/20/21) are genuine zeros.

## Regenerating

```bash
npm run revenue     # cash-basis revenue + refund discrepancies
npm run cogs        # merchandise COGS + payment fees, with coverage report
npm run ad-spend    # Meta spend, EUR -> USD
npm run overlap     # related-party check
npm run fill-pnl    # writes the xlsx from all of the above
```

Regenerate close to the Aug 17 deadline. Ad spend accrues live, the EUR→USD
rate moves, the token split above is a snapshot, and supplier invoices for
the 20 currently-unshipped orders (plus the 4 missing ones) will land
between now and then — all of which shift the loss. Re-read this file's
figures against a fresh run rather than trusting them as fixed constants.
