# P&L Methodology

`financials/pnl-sloane-pearl.xlsx` is the filled official Devpost P&L
template, generated by `financials/scripts/fill-pnl-template.ts`. This file
explains where each number comes from — it is not a second copy of the
numbers themselves, to avoid two sources of truth going out of sync.

**Figures below are the final regenerate, run 2026-08-14** — replacing the
2026-08-13 snapshot with one change: row 23c's payment-processing fees now
use **real, exact data** (OceanPayments' own transaction export, a real
withdrawal report, Shopify's real billing invoices) instead of the
previously-applied estimated blended rate. Every other line is unchanged
from 2026-08-13. Everything is USD, matching the template's own
`Currency: USD` header.

**Context worth stating plainly:** as of this regenerate, Sloane & Pearl is
not actively testing new products or generating new revenue — the operator
has paused active operation of the store. The figures below still reflect
real, cash-basis activity that occurred during the compliance window; they
are not projected or extrapolated forward. August's partial-month figures
reflect orders/spend that occurred before the pause, not ongoing activity.

## Cash basis

The template's legend mandates it: *"You must record revenue and expenses
using the 'cash basis' method. 'Cash basis' is a financial accounting
method where revenue is recorded when cash is received, and expenses are
recorded when cash is paid out."* Applied as:

- **Revenue** counts only cash actually received and retained. `pending`
  orders (cash not yet received) and `voided` orders are excluded, and
  refunds are netted out of the month they belong to.
- **Expenses** count cash actually paid out. Merchandise cost is
  recognised on the supplier's invoice, not at the moment of sale — so an
  order shipped but not yet invoiced carries no COGS yet, correctly.

### Row 23a — Meta ad spend

`getSloanePearlSpendByMonth()`, Sloane & Pearl's own dedicated ad account
(`act_1115325060591696`). Same figure that answers the submission form's
"Marketing and Customer Acquisition Spend" question.

**Currency conversion:** the account bills in EUR; this regenerate used a
live rate of **1 EUR = 1.1567 USD** (fetched 2026-08-14T13:45 UTC by the
platform's own FX refresh). This moves slightly on every re-run and is not
a bug — it's why the ad spend total moved a few dollars from the prior
snapshot even though nothing about the underlying spend changed.

### Row 23c — Payment processing fees — **real data, not an estimate**

**$1,394.74 total**, real throughout — the estimated 7.835% blended rate
used in the prior two regenerates has been fully replaced with exact
figures sourced directly from the operator's real financial records. Four
real components:

1. **$41.27 exact** — Shopify-native payment fees on the 14 orders
   processed that way (`Order.processingFeeShop` etc.), unchanged from
   every prior snapshot.
2. **$800.92 real** — OceanPayments' own transaction-level export

   sheet, 246 rows scoped to `sloaneandpearl.com`/`pdmnf1-c0.myshopify.com`),
   summing every real per-transaction fee column (`Trans Fee`, `SaaS Fee`,

   200 transactions, $18,904.78 gross — independently cross-validated
   against this repo's own DB-derived "200 gap orders, $18,904.78 gross"
   figure, an exact match), Failed attempts ($8.70 — a real cost even
   though the payment itself failed), and Refunds ($6.50). Covers
   2026-06-18 through 2026-08-10 — confirmed to be the *complete*
   OceanPayments population: every order dated before 2026-06-18 (14
   orders total) carries Shopify-native fee data instead, verified
   directly against the database (`Order.processingFeeShop` populated on
   all 14), so there is no earlier gap this file is missing.
3. **$180.00 real** — the withdrawal fee, confirmed at a flat **$45.00 per
   withdrawal** (operator-confirmed, cross-referencing OceanPayments'
   `Withdrawal report` console) across 4 real, successful withdrawals in
   the window (2026-07-20, 07-22, 07-29, 08-05). This component is real
   but was never visible in the transaction-level export — it's charged at
   payout time, not per order — which is exactly why it was flagged as
   still-missing in the prior (estimated-rate) version of this document.
4. **$372.56 real** — Shopify's own "Transaction fees" billing-invoice
   line (`disclosure/pre-existing-resources.md` — the same real invoice
   data that resolved the Shopify plan-fee gap). This is Shopify's charge
   for allowing a non-Shopify-Payments gateway, a cost distinct from
   OceanPayments' own fees (charged by a different party) — previously
   *deliberately excluded* to avoid double-counting against the 7.835%
   estimate, whose "3rd-party gateway surcharge" component was assumed to
   already cover it. Now that the estimate is gone, this real charge is
   included on its own merits with no double-counting risk.

Sum check: 41.27 + 800.92 + 180.00 + 372.56 = 1,394.75 (1¢ rounding against
the $1,394.74 applied — the by-month JSON passed to `fill-pnl` was rounded
per component before summing).

**The two real source files backing this section are deliberately not
committed to this repo.** `Transaction Details-20260814054106.xlsx` and the
raw June-terminal export contain extensive real customer PII across 246+
rows — email addresses, IP addresses, masked-but-real card numbers,
cardholder names — a much larger exposure than anything else this repo
handles. Same policy as every other piece of customer PII documented here
(`evidence/customer-evidence.md`): these go directly into the Devpost
form's revenue-evidence upload at submission time (the checklist explicitly
names "a Stripe dashboard export or bank statement" as an acceptable
format; a redacted OceanPayments settlement export serves the same
purpose), never into git.

**Why this replaced the estimate rather than sitting alongside it.** The
7.835% blended rate (documented in this file's git history, "Row 23c" from
the 2026-08-06 revision) was always disclosed as a stand-in for real data
that didn't exist yet. Once real OceanPayments transaction data, a real
withdrawal report, and real Shopify billing invoices were all in hand, the
estimate no longer had a job to do — real data is more accurate whenever
it's available, and the result happened to come in **$127.72 lower** than
the estimate predicted (narrowing the loss slightly), which is disclosed
here precisely because it moved the number in a flattering direction, not
despite it — the same real-data-first standard applies whichever way a
correction points.

## The xlsx's own formula cells

The blank official template ships every formula cell with a cached value of
`0`. `fullCalcOnLoad` makes Excel and Google Sheets recompute on open, but
anything that reads stored values rather than evaluating formulas — macOS
Quick Look, most xlsx-to-PDF converters, an automated parser — would
otherwise show TOTAL REVENUE, TOTAL EXPENSES and PROFIT (LOSS) as $0.
`fill-pnl-template.ts` therefore computes each total in JS from the same
rounded inputs it writes into the cells, and writes the formula **and** its
real result — verified present (`fullCalcOnLoad="1"`) in this regenerate's
output file.

```bash
                     # REAL_FEES_JSON (real payment fees, see row 23c above)
                     # and the token/personnel/software JSON overrides
                     # derived above and documented in README.md
```

This regenerate (2026-08-14) is intended as the **final** one before
submission, given the store's current paused state means the underlying
activity is no longer moving day to day. If anything changes before Aug 17
(a late invoice, a new order, a corrected fee record), re-run and update
this file rather than trust it as a fixed constant.
